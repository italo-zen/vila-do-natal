## Contexto

O jogo final deve receber versões novas (mapas, missões) sem quebrar o que existe. O formato do conteúdo é barato de definir agora e caro de mudar depois. A build de playtest (HTML único, em artifact) e o GitHub Pages devem usar o mesmo conteúdo.

O jogo não grava progresso: cada carregamento começa do zero (seção 3). Por isso não há formato de save a versionar.

O mapa real (ADR-004) muda o formato de mapas e missões. Como não houve release, o `schemaVersion` 1 não tem conteúdo publicado, e a mudança não exige migração.

## Decisão

### 1. SemVer

- `MAJOR.MINOR.PATCH`, fonte única em `package.json` (`version`).
- **Patch** (1.0.1): correção sem mudar conteúdo nem comportamento de conteúdo existente.
- **Minor** (1.1.0): novo mapa, subárea aberta, missão ou texto. Nada que já existia muda de comportamento. Adotar perfil de arte novo também é minor (ADR-003 seção 12).
- **Major** (2.0.0): mudança que quebra conteúdo existente. Evitar.
  - Remover mapa ou missão só conta como major **depois da 1.0**. Antes disso (versão 0.x), o placeholder e outros conteúdos provisórios saem sem contar.
- Release: tag `vX.Y.Z` na `main` → testes → build → GitHub Pages + GitHub Release, com `CHANGELOG.md` (formato Keep a Changelog).
- A versão é injetada na build pelo Vite (`define: { __APP_VERSION__: JSON.stringify(pkg.version) }`) e exibida na tela de título e nos créditos. Nunca digitada à mão em código.
- Duas versões independentes: a do jogo (`package.json`) e o `schemaVersion` (formato do manifesto). Subir o jogo não sobe o schema, e vice-versa.

### 2. Conteúdo como dados

Tudo que é "o que existe no jogo" fica em `content/`; o motor só lê o manifesto e os arquivos que ele aponta.

```
content/
  manifest.json
  art-profiles/   <id>.json          (ADR-003: perfil de arte ativo e demais)
  maps/casa-real/ <subarea>.json     (gerado pelo conversor a partir do Tiled; não editar à mão)
  missions/       marco1.json, parte1.json, parte2.json, parte3.json, enfeites.json (inicio, conducao, conquistas, nick e dica; escrito à mão; partes na seção 2.2; nick e dica na seção 2.3)
  texts/          pt-BR.json
```

A origem dos mapas é o arquivo do Tiled em `maps/casa-real/` (fora de `content/`). O conversor (`docs/conversor-tmx.md`) gera o JSON de cada subárea. Não há mais `content/maps/casa.json`: o placeholder sai.

**Formato do `manifest.json` (`schemaVersion` 2):**

```json
{
  "schemaVersion": 2,
  "contentVersion": "1.0.0",
  "locale": "pt-BR",
  "artProfile": "hd-480x352",
  "maps": [
    { "id": "hall",   "file": "maps/casa-real/hall.json",   "tileset": "tiles_casa" },
    { "id": "sala",   "file": "maps/casa-real/sala.json",   "tileset": "tiles_casa" },
    { "id": "cozinha", "file": "maps/casa-real/cozinha.json", "tileset": "tiles_casa" }
  ],
  "missions": [
    {
      "id": "marco1",
      "file": "missions/marco1.json",
      "maps": ["hall", "sala", "cozinha"],
      "requires": []
    },
    {
      "id": "parte1",
      "file": "missions/parte1.json",
      "maps": ["hall", "sala", "cozinha", "quarto", "escritorio"],
      "requires": ["marco1"]
    },
    {
      "id": "parte2",
      "file": "missions/parte2.json",
      "maps": ["hall", "sala", "cozinha", "quarto", "escritorio"],
      "requires": ["parte1"]
    },
    {
      "id": "parte3",
      "file": "missions/parte3.json",
      "maps": ["hall", "sala", "cozinha", "quarto", "escritorio"],
      "requires": ["parte2"]
    }
  ],
  "texts": [
    { "locale": "pt-BR", "file": "texts/pt-BR.json" }
  ]
}
```

O exemplo mostra só 3 das 8 subáreas da casa real. O manifesto real tem uma entrada para cada subárea gerada. As partes do Marco 2 listam também `quarto` e `escritorio`, que estão no manifesto real e não aparecem neste exemplo.

**Formato de `missions/marco1.json`** (o início do jogo sai do manifesto e vai para a missão; `nick` e `dica` na seção 2.3):

```json
{
  "id": "marco1",
  "inicio": { "mapa": "hall", "spawn": "elevador", "paginas": ["intro.1", "intro.2", "intro.3", "intro.4"] },
  "conducao": {
    "luzes": { "mapa": "sala", "x": 3, "y": 7, "direcao": "baixo" }
  },
  "conquistas": { "luzes": "conquista.luzes" },
  "nick": {
    "dorme": { "mapa": "sala", "x": 8, "y": 5, "direcao": "baixo" },
    "alvo": "sala"
  },
  "dica": {
    "porta": "dica.porta",
    "luzes": { "dormindo": "dica.luzes.dormindo", "acordado": "dica.luzes.acordado" }
  }
}
```

- `inicio`: a entrada do jogo, por spawn (é o nascimento da introdução).
- `conducao`: por chave de fase, o destino da condução automática depois da fase (ADR-004 seção 11). Campos: `mapa` (id de `missions[].maps`), `x` e `y` (tile, local à subárea) e `direcao` (de chegada: `cima`, `baixo`, `esquerda` ou `direita`). Não é spawn: o destino fica no arquivo da missão, não no mapa (GDD 14.11.3, regra D7).
- `conquistas`: por chave de fase, a chave de texto da tela de conquista. Saiu de dentro da entrada da fase, porque conquista não é condução.
- Chaves de fase são minúsculas, como o valor de `Fase` no domínio (`luzes`). O nome de exibição segue o GDD ("Luzes"). `porta` também é `Fase` (fase da porta, sem `conducao`, mas com `dica`).
- `nick` e `dica` (seção 2.3) ficam no arquivo da missão, como `conducao`. O `missions[]` do manifesto não ganha esses campos (ADR-005 seção 2.1).

**Regras do manifesto:**
- `schemaVersion`: formato do próprio manifesto. O motor recusa versão maior que a que entende, com mensagem clara. Hoje entende só a 2; a 1 é recusada, porque não há conteúdo publicado com ela.
- `id`s são únicos. `file` é relativo a `content/`. `maps` de uma missão, `requires` e as chaves de texto referenciam ids; `validarManifesto()` garante que as referências existem. Renomear um id é ajuste interno de conteúdo, mas só se houver necessidade.
- `missions[].maps` lista ids de `maps[]`: as subáreas abertas na missão (ADR-004 seção 9). Uma subárea que não está na lista não é carregada.
- `inicio` (no arquivo da missão) aponta para spawn que existe, em subárea de `missions[].maps`. `conducao` aponta para tile andável de subárea de `missions[].maps`, com rota a partir do início. `conquistas` e as chaves de `conducao` são fases válidas (`validarConteudo`, ADR-004 seção 8, itens 9, 12 e 13).
- `artProfile`: opcional, padrão `gba-240x160` (ADR-003 seção 12). O Marco 1 no perfil HD declara `hd-480x352` explicitamente.
- O motor não conhece mapa por nome. `validarConteudo()` (application, testado) checa ids duplicados, referências quebradas e `schemaVersion`; na build, a validação roda em um teste Vitest sobre o `content/` real.
- Textos usam chaves e variáveis: `"intro.hall": "Oi, {nome}! O tio Ítalo e a tia Nath precisam de ajuda."`; `{nome}` e `{ele_ela}` vêm do `Sobrinho`.
- Assets (sprites, áudio) ficam na pasta do perfil (`assets/<perfil>/`, ADR-003 seção 3) e são referenciados por id no mapa e na missão.

**Regra: novo mapa = arquivos novos + uma linha no manifesto (`maps[]`).** Adicionar mapa e missão não pode exigir mudança em `src/`. Abrir uma subárea numa versão menor é acrescentar o id em `missions[].maps`. Teste obrigatório (Marco 1, item 013): um mapa de teste adicionado a um manifesto de fixture carrega sem alterar o motor. Se uma novidade exigir código novo (mecânica nova), isso é mudança de motor e vai em outro item.

### 2.1 Mudanças do schema 1 para o 2

| Campo | Schema 1 (placeholder) | Schema 2 | Motivo |
|---|---|---|---|
| `schemaVersion` | 1 | 2 | Formato mudou |
| `startMap` (raiz) | `"casa"` | Removido. Vai para `inicio` em `missions/marco1.json` | Início é da missão, não do conteúdo |
| `maps[]` | Uma entrada: `casa` | Uma entrada por subárea gerada | ADR-004 |
| `maps[].rooms` | Lista de cômodos | Removido: uma subárea é um cômodo | ADR-004 |
| `missions[].map` (id único) | `"casa"` | Removido. `missions[].maps` (lista) | Marco 1 abre 3 subáreas |
| `artProfile` | Opcional, `gba-240x160` | Opcional; o Marco 1 no HD declara `hd-480x352` | ADR-003 |

**Migração: nenhuma.** Não há save (seção 3) e não há release com schema 1. O motor passa a ler só o schema 2. O placeholder `casa` sai do conteúdo no mesmo PR da troca do motor (backlog 026), porque o motor atual ainda lê `startMap` e `casa`.

**Revisão de 2026-11-08 (item 036, condução automática).** `nascimentoPorFase`, presente no schema 2 do Marco 1.2 que ainda não foi publicado, vira `conducao` (destino da condução). `conquista` sai da entrada da fase e vai para `conquistas`. O manifesto continua `schemaVersion` 2 e não há migração, porque não houve release. O Dev troca o campo e os textos de `content/missions/marco1.json` no mesmo PR do motor.

**Escopo do `schemaVersion` (esclarecimento).** O `schemaVersion` vale para todo arquivo de conteúdo que o manifesto aponta (missões, mapas, perfis e textos), e não só para o próprio manifesto. Até a 1.0, mudar campo de missão ou de mapa não exige número novo nem migração. Depois da 1.0, é mudança de schema, com migração se já houver conteúdo publicado.

### 2.2 Marco 2: peças, missões e chaves (item 061, GDD 15)

**`schemaVersion` continua 2.** A mudança é aditiva: um tipo novo de objeto de mapa (`peca`, ADR-004 seção 6), três missões novas (`parte1` a `parte3`) e chaves novas de texto. Nenhum campo existente muda de sentido. Pela regra "Escopo do `schemaVersion`", até a 1.0 isso não pede número novo nem migração. O motor continua recusando `schemaVersion` maior que 2. Subir para 3 só se um campo existente mudar de forma (por exemplo, `maps` deixar de ser lista).

**Valores de `luzes` na planta girada.** `conducao.luzes` = `{mapa: "sala", x: 3, y: 7, direcao: "baixo"}` (ADR-004 seção 12). Antes da rotação, eram `x: 7, y: 7, direcao: "direita"`.

**Missões do Marco 2.** No manifesto (`missions[]`, ver o exemplo da seção 2):
- `parte1` requer `marco1`; `parte2` requer `parte1`; `parte3` requer `parte2`. A cadeia é `marco1` ← `parte1` ← `parte2` ← `parte3`. `validarManifesto` recusa `requires` inexistente e ciclo.
- `maps` de cada parte = `["hall", "sala", "cozinha", "quarto", "escritorio"]`: as áreas abertas enquanto a parte é a missão ativa (ADR-004 seção 9.1). A Suíte e os banheiros não entram. A Suíte entra só se a pergunta 26 abrir o caminho [TBD].

`missions/parte<N>.json`:

```json
{
  "id": "parte1",
  "conducao": { "parte1": { "mapa": "sala", "x": 3, "y": 7, "direcao": "baixo" } },
  "conquistas": { "parte1": "conquista.parte1" }
}
```

- `conducao.parteN`: destino da condução, com os mesmos campos de `luzes`. Nas três partes, o destino é a Sala, (3, 7), de frente para a árvore (GDD 15.3.6). O ponto de partida não é dado: é o vizinho livre da peça de onde o A foi dado (ADR-004 seção 11.1).
- `conquistas.parteN`: chave de texto da tela de conquista (`conquista.parte1`, etc.).
- Chaves de fase: `parte1`, `parte2`, `parte3`, minúsculas, valores do enum `Fase`, como `luzes`. As três entram no enum (backlog 051, critério 4).
- Ligação com a peça: a peça de ordem N é a da missão `parteN`. Não há campo extra: a ordem liga as duas. A caixa de enfeite (objeto `enfeite`, ordem 4) liga-se a `enfeites` (ADR-006 seção 2).
- Nenhuma parte tem `inicio`. O início do jogo continua em `marco1`.

**Chaves de texto (`texts/pt-BR.json`).** Nomes com padrão, para o domínio montar a chave sem tabela:

| Chave | Uso | Quem monta |
|---|---|---|
| `conquista.<fase>` | Tela de conquista (`luzes`, `parte1` a `parte3`) | `conquistas` da missão |
| `arvore.estado.<n>` | Exame da árvore, `n` = 1 a 3 (4 só se a pergunta 37 for B, ADR-006 seção 13). O estado 0 usa `arvore.desmontada` | domínio, pelo estado da árvore |
| `arvore.chegada.<n>` | Diálogo de chegada depois da peça `n` | domínio, no encaixe da peça `n` |
| `aviso.peca<N>.antes<M>` | Aviso "ainda não" da peça N, com a parte M ainda não encaixada (M < N) | domínio (regra abaixo) |
| `porta.fechada` | Porta fechada (P1, P4 e P6, e par com área fechada) | `texto` do objeto ou padrão |

- **Avisos.** M é a menor ordem entre 1 e N−1 que ainda não está encaixada. Há exatamente três avisos, para N = 2 e N = 3: `aviso.peca2.antes1`, `aviso.peca3.antes1` e `aviso.peca3.antes2`. Cada um tem duas páginas (GDD 15.8). A validação confere as três (ADR-004 seção 8, item 19). Além delas, o Marco 4 traz `aviso.enfeite.antes3`, da caixa de enfeite, com duas páginas (ADR-006 seção 2.4).
- Nenhuma chave cita nome de pessoa da família (backlog 034).
- Os textos exatos das conquistas e dos diálogos seguem GDD 15.8 e são conferidos por teste de string (backlog 051, critério 3).
- Campos `nick` e `dica` das partes: seção 2.3 (valores por missão na tabela de ADR-005 seção 2.3).

### 2.3 Marco 3: `nick` e `dica` nas missões de fase (item 079, ADR-005 seção 2)

**Onde.** Em `missions/<id>.json` das quatro missões de fase (`marco1`, `parte1`, `parte2`, `parte3`), junto de `conducao` e `conquistas`. Não vai no TMX (o tile de dormir depende da fase, não da subárea) nem no manifesto. O `missions[]` do manifesto (seção 2) não muda.

**Formato.** Exemplo `marco1` na seção 2. Para `parte1` a `parte3`, a forma é a mesma; os valores estão na tabela de ADR-005 seção 2.3.

Campos:
- `nick.dorme`: `{ mapa, x, y, direcao }`, onde o Nick dorme durante a fase. `mapa` é id de `missions[fase].maps` (N002) e nunca `hall` (N003). `x` e `y`: tile livre da subárea (N004 a N007). `direcao`: `cima`, `baixo`, `esquerda` ou `direita`.
- `nick.alvo`: id de subárea de `missions[fase].maps` (N010) que contém o item da fase (N011: `marco1` tem o interruptor; `parteN` tem a peça de ordem N). É subárea, não tile: o farejar não revela posição (ADR-005 seção 4.2).
- `nick.depois`: removido em 0.8.0 (ADR-006 seção 6). Qualquer ocorrência é N008.
- `dica`: uma chave por fase. Valor **texto** vale para os dois estados (ex.: `"porta": "dica.porta"`). Valor **objeto** tem `dormindo` e `acordado`. `livre` saiu em 0.8.0 (ADR-006 seção 6). Qualquer ocorrência é N014.

Regras:
- `nick` e `dica` são **obrigatórios** nas quatro missões de fase. Ausência é N001 (ADR-005 seção 2.5). Entram no mesmo PR do validador, sem janela em que o jogo quebra.
- `x` e `y` `null` só valem como rascunho. No conteúdo entregue, `null` é N001. Quem fecha é a Arte, no mesmo PR (item 074). As direções e os tiles de `parte1` a `parte3` também são da Arte.
- `schemaVersion` continua 2 (aditivo, seção 2.2). Até a 1.0, sem migração.
- Validação: `validarNick` (N001 a N014, ADR-005 seção 2.6), chamado por `validarConteudo`. Todas são erro.

Formato: `string` ou `string[]` (uma entrada por página). Teto aproximado de N013: 84 caracteres por página (3 linhas de 28). Nenhuma chave cita nome de família (backlog 034).

### 2.4 Marco 4: fase `enfeites`, campo `final` e caixa (item 087, ADR-006)

**`schemaVersion` continua 2.** A mudança é aditiva: o campo `final` (opcional) em `missions[]`, a missão `enfeites` e o objeto `enfeite` (ADR-004 seção 6). Pela regra "Escopo do `schemaVersion`", até a 1.0 isso não pede número novo nem migração.

Entrada nova em `missions[]` (o exemplo da seção 2 mostra só 3 das 8 subáreas; esta entrada segue a lista de 5 subáreas das partes):

```json
{ "id": "enfeites", "file": "missions/enfeites.json", "maps": ["hall", "sala", "cozinha", "quarto", "escritorio"], "requires": ["parte3"], "final": true }
```

- `final`: booleano, opcional, padrão `false`. Marca a missão de fim. Regras T001 a T005 (ADR-006 seção 9): no máximo uma com `final: true` no manifesto; no conteúdo real, exatamente uma; ninguém a exige; toda missão é ancestral dela; a fase dela é a última de `FASES`.
- `missions/enfeites.json`: sem `inicio`; com `conducao`, `conquistas`, `nick` e `dica`, como nas fases (ADR-006 seção 8.2). A ADR-005 seção 2.1 continua valendo: `nick` e `dica` não entram no manifesto.
- O motor lê `final` do manifesto. `Fase` ganha `enfeites` e perde `creditos` (ADR-006 seção 1).
- Variável nova de texto: `{versao}`, em `creditos.versao`, preenchida com `__APP_VERSION__` (seção 1 deste ADR). Nunca digitada.

### 3. Decisão: sem persistência na v1.x

Decidido pelo Diretor em 2026-11-07 (registrado em `decisions.md`): o jogo não grava progresso. Toda vez que é carregado, começa do zero. O título tem só "Começar" e "Como jogar", sem "Continuar".

Consequências práticas:
- Não há `localStorage`, `saveVersion`, migrações, backup de save, nem porta de persistência. O `Progresso` vive só em memória, durante a sessão (ADR-001).
- Nenhum código em `domain/`, `application/` ou `infrastructure/` lê ou grava estado entre sessões.

Se um dia houver save (por exemplo, "continuar de onde parou"), isso exige **novo ADR** antes de qualquer código. Esse ADR deve definir: formato com `saveVersion`; uma função de migração para cada mudança de formato, com testes usando fixtures de cada versão; e o comportamento para save corrompido ou de versão futura. Sem esse ADR, não se implementa persistência.

## Consequências

Positivas:
- Novos mapas e missões entram sem tocar no motor, com validação automática do manifesto.
- Sem save, não há progresso guardado para migrar nem estado corrompido para tratar: menos código e menos casos de teste.
- Duas versões independentes (jogo e schema do manifesto) evitam acoplamento entre lançar release e mudar formato de conteúdo.

Negativas:
- Disciplina: toda mudança de `schemaVersion` exige teste de validação atualizado; ids são referência interna e renomear exige ajustar todas as referências.
- Tiled + conversor + manifesto + missão formam uma cadeia de quatro peças coordenadas. O golden file do conversor e `validarConteudo` sobre o `content/` real são essenciais.
- Quem recarrega a página perde o progresso da sessão. Aceito pelo Diretor, porque a sessão é curta e sempre começa do início.

## Alternativas descartadas

1. **Conteúdo embutido em TypeScript.** Mais simples, mas cada mapa novo mexe no código e exige revisão do motor. Descartada.
2. **Descoberta automática por glob de `content/maps/*`.** Sem manifesto não há ordem, dependências nem validação, e a build de HTML único precisa de lista explícita. Descartada.
3. **Progresso salvo em `localStorage`, com versão e migrações.** Descartada pelo Diretor em 2026-11-07: o jogo sempre começa do zero. Só volta a ser considerada por novo ADR (seção 3).
